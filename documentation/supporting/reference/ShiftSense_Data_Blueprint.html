ShiftSense Data Blueprint

What data goes into ShiftSense, who provides it, how forgiving the input is, how a change spreads to rosters and decisions, and what comes out for each role. This is the agreement to build against. Status 18 Oct 2026: built and tested (reference data, smart conversion, change engine, approvals, situations, contracts, base pack, Data hub, downloads). Not yet: moving the rest of the app onto PostgreSQL, a scheduled watched folder, the event calendar view, call-volume based actual service levels, and the attendance feed.

Draft 2 · 18 Oct 2026 · changed in this draft: any-format input with AI-assisted conversion, enforced mandatory fields, and situation-based inputs for holidays, outages, protests and disasters · terms such as "effective date" or "freeze window" are explained where they first appear and in the handbook glossary.

What is decided

  • PostgreSQL for the pilot. A proper database server replaces the single SQLite file for the pilot. The local demo can keep SQLite; both go through one data layer, so the app code is the same.
  • Data sources for the pilot: employee details, employment contracts, client contracts with their service levels, updated rules, and any new condition (holidays, campaigns, outages, training and similar).
  • Five roles stay. No new role is added. Looking after reference data becomes a responsibility inside existing roles (see who owns which data).

Principles

PrincipleWhat it means in practice
Accept input in any formatExcel, CSV, a pasted table, pasted free text (an email or chat message), or a manual form. Rules convert what they recognise instantly; AI converts the rest into the required format. A person checks the result before it is applied.
Mandatory means mandatoryEach kind of data has a short list of fields that must be present. If they are missing, the system asks for them. Neither the rules nor the AI ever invent a mandatory value.
One owner per factEach kind of data has one role that submits it and, where it matters, a second role that approves it. Nobody else can change it.
Every change has an effective dateThe effective date is the day a change starts to count. It can be today or in the future (for example a new contract from 1 November). Old versions are kept; nothing is overwritten.
Changes spread automatically, people still decideAn updated agent, contract, rule or service level is re-checked against the roster at once. The system flags what it breaks and proposes fixes, but it never edits a published shift by itself.
Plain-language errors, row by rowEvery problem names the row, the column, what is wrong and how to fix it. Values the system can safely correct are corrected and shown. Good rows are not held back by one bad row, except for rules and contracts.
Outputs are labelled and visual firstEvery screen and file says what it is (recorded, planned or forecast), when it was produced, whether it is live or demo, and where the numbers came from. Charts always come with a one-line takeaway and the same numbers as a table.

Who owns which data

Admin stays oversight-only, so Admin does not edit operational data (people's skills, contracts, rules). The Analyst becomes the data steward: the person who loads and maintains reference data, usually from HR or client files. Changes that affect cost or service promises need a second person to approve, which is Ops.

How it is entered

  • Analyst: upload the HR export (all employees or only changed ones), or edit one person on their agent card.
  • Team Lead: "Propose a change" on an own-team agent (for example, finished Banking-EN training). The Analyst accepts or declines it with a reason.
  • Agent: updates own shift and day-off preferences on My work. These are wishes for the next plan and never force a change.

What a change does

  • Skill removed: future shifts on that queue break the "trained queues only" rule. In the freeze window, an alert goes to the team lead with a ready fix. On later days, the Analyst gets a re-plan draft.
  • Skill added: recovery can use the person straight away, and the next plan can too.
  • Team changed: ownership of their alerts, requests and reminders moves to the new team lead, and both team leads are told.
  • Last working day set: shifts after it are released, which shows as gaps. Pending requests after that date are closed with a reason.
  • Night permission removed: their night shifts are flagged the same way as a removed skill.
  • Contract changed: weekly hours and shift counts are re-checked from the effective date.
  • Preferences changed: used at the next re-plan only.

Username, name, role, team, linked employee ID, work email, contact preference and active flag, maintained by Admin as today. With single sign-on later, roles can come from company directory groups. This is part of the separate sign-in work.

Ways to put data in

Manual form. One record at a time: plain labels with units, drop-downs where possible, problems shown as you type, and an impact preview before saving ("this affects 3 shifts this week").
Excel or CSV file. Any layout: our template, an HR export, a hand-made sheet, dates across columns, merged headers. Drag it in and pick the sheet if there are several.
Copy and paste. A table copied from Excel or Google Sheets, or plain text such as an email or chat message ("Aarav and Sneha are off 12 to 14 Oct for training").
Round-trip and scheduled files. Download current data as a filled template, edit, upload back, and see only what changed. HR and telephony exports dropped in an agreed folder are picked up on a schedule.

All four end in the same place: the same checks, the same preview, the same confirmation, the same log.

Smart conversion (AI-assisted)

Turns whatever was given into ShiftSense's required format. It follows the product rule set earlier: deterministic rules first because they are instant and exact, AI only for what rules cannot read, and a person always confirms.

Read the input→Rules convert what they recognise→AI converts the rest→Checks + mandatory fields→Side-by-side preview→Person confirms→Apply and log
StepWhat happens
ReadFiles, pasted tables and pasted text are read as they are. Title rows, blank rows, merged cells and multiple sheets are handled.
Rules firstKnown headers, saved mappings from earlier uploads, and the value formats listed below are converted without AI. A file in a shape seen before usually needs no AI at all.
AI for the restUnknown headers ("Desig.", "Proc/Lang"), unusual layouts (one column per date, a roster grid, codes like "M/E/N/WO"), and free text are turned into structured rows. Each converted value carries a confidence level and a link back to the exact cell or sentence it came from.
ChecksExactly the same checks as any other input: valid queues and teams, date sense, duplicates, hard rules. Mandatory fields are checked last; anything missing is listed for the person to fill in.
PreviewOriginal next to converted. Corrected values are marked, low-confidence values are highlighted, and missing mandatory fields are shown as empty boxes to fill in place.
Confirm and learnThe person accepts, edits or rejects each row. Accepted column matches are saved, so the next file from the same source converts with rules alone.

Guardrails

  • Never invents. If a mandatory value isn't in the input, it stays empty and the person is asked. A guessed date, ID or queue is never applied unconfirmed.
  • Never applies. AI output is only a proposal. Approval and all checks happen exactly as for manual input.
  • Sends as little as possible. For mapping columns, only headers and a few sample rows go to the AI. Full content goes only for free text that has to be read. Passwords and account data are never sent.
  • Can be switched off. Without AI, rules, saved mappings and manual column matching still work. Free text then has to be entered through the form.
  • Logged. Each applied change records "converted by rules" or "converted by AI", who confirmed it, and the original input.
  • Before the pilot: sending employee data to an AI provider needs EXL's data-processing agreement, or an AI model hosted inside EXL. Until then the pilot runs with AI conversion switched off or on non-personal data only (for example call volumes and event descriptions).

  • Employees, leave, volumes, attendance: good rows can be applied while bad rows are held back. A "rows to fix" Excel file comes back with an extra column explaining each problem; fix it and upload just that file.
  • Contracts, client service levels, rules: all or nothing. A half-applied rule set would be unsafe.
  • Duplicates and stale files: the same employee twice in one file is an error. A round-trip file edited after someone else changed the same records gets a warning listing those records.
  • Every applied change is logged with who, when, the file or form it came from, before and after values, and the effective date. A data change can be reversed by applying the previous version, which is also logged.

How a change spreads

Submit→Check→Impact preview→Approve (where needed)→Apply on the effective date→Re-check roster and decisions→Act: alerts, re-plan draft, notices→Log
  • Impact preview before anything is applied: which people, shifts, queues, requests and alerts are touched, plus coverage and cost before and after.
  • Freeze window (today and started days): problems become alerts for the team lead with a ready fix, exactly like an absence today.
  • Later days: the Analyst gets a re-plan draft built automatically, labelled with the change that caused it. It still needs validate, review and publish.
  • Future-dated changes are stored and applied when their effective date arrives, with the same re-check at that moment.
  • No silent change: the system never edits a published shift on its own. It flags, proposes and notifies.
  • People affected are told: the agent (for their own record), their team lead, and Ops for anything that changes service promises or cost.

Output standards

  • Visual first, numbers always available. Each view has a chart or grid, a one-line takeaway ("Claims-HI is 6 people-hours short on Thursday evening"), and a Data button with the same numbers as a table.
  • Same visual language everywhere. Recorded figures in solid colour, planned in outline, forecast as a shaded band. Status colours are the same on every screen and in every file.
  • Plain column names with units ("Gap (people-hours)", "Cost (₹, configured rates)"). People's names next to IDs.
  • Every file explains itself. Excel exports include a "Read me" sheet: what it is, as-of time, live or demo, source, definitions of every column, and what is recorded, planned or forecast. Header rows are frozen and formatted.
  • Formats: Excel for working files, CSV for other systems, calendar files (.ics) for personal schedules, and a print-friendly page for schedules and briefs.
  • Scoped by role on the server: an export contains exactly what that person may see, and the export itself is logged.

  1. Foundation: the data layer on PostgreSQL (with SQLite for the demo), proper tables, migrations, moving current data across, scheduled backups.
  2. Change engine: change requests with effective dates, approval, impact preview, apply, re-check, alerts and re-plan drafts, data change log.
  3. People and leave: employee forms, team-lead proposals, agent preferences, smart conversion (rules first, AI for the rest, side-by-side preview, mandatory-field prompts, saved mappings), rows-to-fix files, partial apply, round-trip templates.
  4. Agreements, rules and situations: contract types, client contracts and service levels, in-app rules with versions, situation forms (holiday, outage, protest, disaster and others) with quick report and continuity mode, shared calendar.
  5. Outputs: role packs with Read me sheets, calendar files, print views, client service-level report, data quality dashboard.
  6. Actuals: call volume import (forecast accuracy, actual service level), optional attendance feed.
  7. Sign-in hardening alongside: password change and reset, password rules, lockout, session timeout, then single sign-on.
